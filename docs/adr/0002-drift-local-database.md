# ADR-0002：选用 drift 作为本地数据库

**Status**: Accepted (2026-07-19)

关联：[技术架构设计-第 6 节](../03-技术架构设计.md)、[PRD-Implementation Decisions](../02-PRD-产品需求文档.md)

## Context

产品数据全部默认本地存储（隐私原则 US-K01），需要持久化：专注时段与阶段事件流（计时引擎防杀恢复的事实来源）、每日应用使用统计、应用规则（白名单/拦截）、目标与成就。数据特征：

- 结构化、关系型（session ↔ phase_event 一对多）；
- 统计页/报告页需要按时间、标签、包名做多维聚合查询；
- 统计页希望数据变更自动刷新（流式查询）；
- schema 会随 V0.1→V1.0 演进，需要可靠的迁移机制。

候选方案：

1. **drift**（原 moor）：类型安全的 SQL 封装，编译期生成 DAO，支持流式查询（`watch()`）与版本化迁移；
2. **hive**：纯 KV，无关系与聚合查询能力，社区维护活跃度下降，停更风险；
3. **isar**：查询能力强，但项目维护状态存在不确定性（停更风险），且代码生成链路重；
4. **sqflite**：官方维护但太底层，手写 SQL 字符串无类型安全，迁移与流式刷新需自行封装。

## Decision

选用 **drift** 作为唯一本地数据库：

- 用类型安全的 Dart 表定义描述 schema（草案见 [技术架构设计-第 6 节](../03-技术架构设计.md)），编译期检查 SQL；
- 统计/报告页通过 `watch()` 流式查询对接 Riverpod `StreamProvider`，数据变更自动刷新 UI；
- schema 演进使用 drift 自带 migration，每个版本号的升级路径写入迁移测试；
- Repository 接口定义在 Core 层（纯 Dart），drift 实现放在 Platform 层，保证 Core 无 Flutter/三方依赖、可单测。

## Consequences

**正面**：
- 类型安全消除手写 SQL 的运行期错误；复杂聚合（专注报告、标签分布）直接表达；
- 流式查询 + Riverpod 形成「数据库 → UI」的响应式链路，省去手动刷新逻辑；
- 迁移机制支撑 V0.1→V1.0 的 schema 演进，升级不丢用户数据。

**负面**：
- 代码生成增加构建时间（build_runner），需纳入 CI 缓存；
- 团队需学习 drift 的表定义语法，成本低于手写 SQL 维护成本。

**替代方案放弃原因**：hive/isar 的维护不确定性与关系查询能力不足；sqflite 过于底层，类型安全与流式能力需重复造轮子。
