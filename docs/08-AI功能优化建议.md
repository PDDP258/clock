## 1. 结论摘要

现有 AI 链路的**架构是对的**：本地洞察引擎算数、LLM 只做润色、三层静默短路、白名单上传、降级矩阵齐备。问题不在设计，在**四个「会产出错误内容」的实现细节**，以及**三个「第四个 AI 触点就无法维护」的结构债**。

按投入产出比排序，本轮建议做这 4 条（P0，全部是既有代码的小改，无新依赖）：

| # | 问题 | 用户可见的后果 | 改动量 |
| --- | --- | --- | --- |
| **A1** | 环比拿「本周部分周」比「上周完整周」 | 周一打开就看到「退步 95%」并被 AI 当成结论说出口 | 小（口径 + prompt 各一处） |
| **A2** | 缓存只按周键，不感知数据变化 | 周一生成的解读，周日看到的还是「本周只有 25 分钟」 | 小（缓存加指纹 + 一行提示） |
| **A3** | 解析器对模型排版过于敏感 | 答得好好的被判定「解读结果异常」，整块降级 | 小（纯 Dart 解析加固） |
| **A4** | `max_tokens=600` 三个调用共用 | 40 字的点评也要等 ~30s，白等 4~10 倍延迟与 token | 极小（加一个参数） |

P1/P2（质量与增量）见 §4/§5。**如果只做一件事，做 A4**——一行参数的收益最大。

## 3. P0：必改（会产出错误内容）

### A1 环比口径不诚实：部分周 vs 完整周

**现象**：`buildWeeklyReport`（`weekly_report.dart:58-95`）里 `thisWeekMillis` 是「本周一 00:00 至今」，`lastWeekMillis` 是「上周一~上周日全周」，第 91 行直接 `(thisWeek - lastWeek) / lastWeek`。

**后果**：周一 10:00 打开统计页 → 本周 25 分钟 vs 上周 600 分钟 → 环比 **-95.8%**。而 `buildPrompt`（`prompt_builder.dart:36`）把这个数原样写进 prompt，并明确要求「数字必须原样引用，不得自行计算或编造」——**LLM 会忠实地把这个数当成结论说出来**（「本周专注大幅退步，需要反思」）。这不是 LLM 幻觉，是我们喂给它的错误前提。

**为什么这条最严重**：项目从 R1 起反复确立「诚实统计」家风（R4 防假专注、R8 物理不可能行自愈、§6-38(d) 拒绝相对分位），而这是 AI 模块里唯一**主动输出错误结论**的地方——结构化周报的 -95.8% 用户自己能看出「这周才过了一半」，配上 AI 的一段话就会被当成判断。

**修法（推荐 B）**：
- **A（最小改动）**：引擎补 `daysElapsed`（本周已过天数，1~7）与 `isPartialWeek`，prompt 显式声明「本周为进行中的部分周（周一至周X），环比不可比，请勿据此下『退步』结论」；UI 环比文案同步标注「（部分周）」。改动小但属于「靠提示词救」。
- **B（推荐，口径修正在数据层）**：`changeRatio` 改成**对齐进度口径**——上周只截取到「上周同一星期几的同一时刻」。例：周三 15:00 时，上周基线 = 上周一 00:00 ~ 上周三 15:00。这样环比天然可比，prompt 里也不需要免责声明。
- **C（配合 §5-B3）**：改用**近 4 周滚动中位数**做基线，单周噪声更小。工作量最大，建议与 B3 一起做。

> 建议落地路径：先 B（口径），`changeRatio` 语义变更需要在 `weekly_report.dart` 头注释与 06 PRD 同步说明；A 作为 B 的过渡或叠加。

### A2 缓存只按「周」不按「数据指纹」→ 一周内持续显示过时解读

**现象**：`AiSettingsNotifier._kCache` 存 `{week, text}`（`ai_controller.dart:301`）。`requestInterpretation` 命中同周即直接回看（第 256-274 行），`autoInterpretIfDue` 看到本周有缓存就静默短路（第 327-335 行）。

**后果**：周一第一轮完成时自动生成了一份解读（内容基于「本周 25 分钟」）。此后整周数据一直在涨，但用户周日打开统计页看到的**仍然是那份周一快照**——除非他自己想到去点「重新解读」。**这是每周都会发生的、用户可见的错误内容**，比 A1 更常触发。

**修法**：
1. 缓存体加 `fingerprint`：由 `(sessionCount, thisWeekMinutes, interruptionCount)` 拼一个短哈希（`insight.dart` 加个 `fingerprint` getter，纯 Dart 可测）。
2. 命中缓存时比对指纹，分两档处理（严守安静原则，**不自动重发**）：
   - 变化 < 阈值 → 照常显示缓存，什么都不说；
   - 变化 ≥ 阈值（如 +2 轮或 +20% 时长）→ **仅一行被动提示**「数据已更新，点『重新解读』刷新」。
3. 可选：`autoInterpretIfDue` 允许**每周最多一次**因指纹变化触发的自动刷新（严格限次，否则就变成打扰）。
4. 若采纳 C1（建议兑现追踪），缓存结构本来就要改成按周列表，可一并落地。

### A3 解析器太脆：模型排版差异直接导致整块降级

**位置**：
- `parseInsightResponse`（`prompt_builder.dart:56-80`）
- `parseAskAnswer`（`ai_ask.dart:129-144`）
- `parseDailyComment`（`daily_comment.dart:40-56`）

**三个具体脆弱点**：

| 脆弱点 | 触发场景 | 后果 |
| --- | --- | --- |
| 只用 `\n\s*\n` 切段 | Kimi/通义 常用单换行分段，或整段无空行 | `parts` 只有 1 项且不含「建议：」→ 返回 null → **整体降级**，尽管内容完好 |
| `startsWith('建议：')` 精确匹配 | 模型输出 `**建议：**`、`- 建议：`、`## 建议：` | 同上，整体降级 |
| 只取首个非空行 | 模型先来一句「好的，根据你的数据：」 | 问答/点评展示这句废话 |

**修法**（纯 Dart、无依赖、可测，收益是**降级率直接下降**）：
1. 分段落：先按空行切，`parts.length < 2` 时回退按单换行切。
2. 建议段识别改正则：`^\s*[-*#>‧\s]*\**\s*(建议|我的建议|下周建议)\s*[:：]`（`before` 允许 Markdown 装饰）。
3. 统一做一次 Markdown 清洗：剥 `**bold**`、`## `、`- `、`1. ` 前缀。
4. 问答/点评：设一个**客套开场白名单**（「好的」「根据」「以下是」「从数据看」起头且长度 > 12 的行）→ 跳过继续往下找。
5. 测试补：单换行分段、`**建议：**` 加粗、前置客套话、混合 Markdown 四个用例。

> 参考 §6-46(d) 的教训：「一行归并文案会杀死真机排查」。同理，**一个过严的解析器会把好答案判成坏答案**，而且用户和开发者都看不到原始输出（模型回答根本没落盘）。

### A4 `max_tokens=600` 三处共用 → 白等 4~10 倍延迟

**现象**：`OpenAiCompatibleLlmProvider.maxInsightTokens = 600`（`deepseek_provider.dart:99`），`generateInsight` 对所有调用一视同仁。但当日点评契约是 **≤40 字**、问答是 **≤80 字**——600 tokens 的预算对它们是 4~10 倍浪费。

**为什么这条代价最高**：非流式 `/chat/completions` 要等**整段生成完**才返回响应头（§6-46(a) 自己写的教训：「600 tokens ÷ ~20 tok/s ≈ 30s」）。所以 **max_tokens 直接等于用户等待时间**。点评/问答给 600 的预算，用户就是在为不会出现的 500 个 token 干等。

**修法**：
```dart
Future<String?> generateInsight(String prompt, {int maxTokens = 600});
```
- 周报解读：600（保持）
- 周报/当日问答：200（80 字 ≈ 150 tokens 上限）
- 当日点评：120（40 字 ≈ 80 tokens）

预期：点评/问答延迟从 ~30s 级降到 ~6~10s 级，成本同比例下降。**一行参数的改动，收益最大。**

## 4. P1：质量提升

### A5 温度与消息角色

- `temperature: 0.7`（`deepseek_provider.dart:112`）对「数字必须原样引用」的任务偏高，建议 **0.3**；创作性可忽略，数据引用需要确定性。
- 当前把角色设定和约束全部塞在一条 `user` message 里。**拆出 `system` message**（角色 + 硬约束），`user` 只放数据与问题——主流服务商对 `system` 的指令遵循度显著更高。两处都是一行改动。

### A6 数据量门槛：数据太少就不该发请求

**现象**：`requestInterpretation` 只短路「关 / 无同意 / 无 Key」（`ai_controller.dart:245-280`），**不看本周数据量**。周一（或刚清数据后）手动点「AI 解读」→ prompt 里是「本周 0 分钟、上周 0 分钟」，无环比字段 → LLM 只能输出一段鸡汤。自动路径虽然挂在「首轮完成」，但首轮后本周也只有 25 分钟，输出质量依然很差。

**修法**：`WeeklyInsight` 加 `isSufficient`（建议门槛：本周 ≥ 2 个会话 **且** ≥ 60 分钟，或直接 ≥ 60 分钟）；不足则**不发请求**，UI 显示「本周数据还太少，攒够 1 小时后 AI 解读更有意义」。附带收益：**省钱**——现在是「本周第一轮完成」就发请求，这个时点的解读价值最低，等于每周浪费一次请求。

### B2 Prompt 拼接重复两组（口径漂移风险）

周报事实块在 `buildPrompt`（`prompt_builder.dart:27-46`）与 `buildAskPrompt`（`ai_ask.dart:73-92`）**逐行重复**；当日事实块在 `buildDailyPrompt`（`daily_comment.dart:25-36`）与 `buildDailyAskPrompt`（`ai_ask.dart:109-124`）同样重复。

后果：一旦补字段（比如 A1 的 `daysElapsed`、B3 的中断时段分布），**必须改两处，漏一处就是两套口径**，而且 prompt 不一致导致的输出差异极难排查。

**修法**：抽 `weeklyFactsBlock(WeeklyInsight)` / `dailyFactsBlock(DailySummary)` 到 `core/ai/`，四个 builder 共用。纯函数，可单测。

### B3 洞察引擎没吃满已有数据

现有字段（`insight.dart:11-24`）：本周/上周分钟、环比、会话数、轮数、时段四桶分布、最专注时段、连续天数、缓冲天数、中断次数/分钟。

**数据已经在库里、但没进洞察的**（`insight_engine.dart:60-78` 的聚合循环只累加了 count/minutes）：

| 新增字段 | 数据来源 | 价值 |
| --- | --- | --- |
| **中断的时段分布** | `pauses` 已带 `(start, end)` 时间戳，现只累加计数 | **最高**——「怎样减少中断」这道 chip 题现在基本是空谈（LLM 手里只有两个数），有了时段分布才能答出「你的中断集中在晚上」 |
| 中断时长占比 | `interruptionMillis / thisWeekMillis` | 一次算好，LLM 不必自己除（现在 prompt 明确禁止它算） |
| 单次中断平均时长 | 两个既有字段相除 | 同上 |
| 本周最长连续专注段 | `DailySummary` 已有 `longestSegmentMillis`，周维度没有 | 回答「最长一段怎么用好的」需要它，现在这题只能泛泛而谈 |
| 近 4 周滚动中位数 | 需扩查询窗口（现为 2 周） | 替代噪声大的单周环比（配合 A1-C） |

**注意**：新增字段要**同步进 `toUploadJson` 白名单**（`insight.dart:62`）——这是有意的手工逐字段列出，新增字段默认不出设备。中断时段分布属于「时段聚合」，与现有 `slot_distribution` 同性质，进白名单没有合规问题；但仍需在 07 §5.1 的表里补一行。

### B1 三个控制器复制同一套管道（第四个触点的债）

`ai_controller.dart`（~340 行）、`daily_comment.dart`（~165 行）、`ai_ask.dart`（~280 行）**逻辑同构**：

```
读 settings → 关/无同意 短路 → 读 key → 空 key 短路 → 读缓存 → 命中回看
→ loading → 写上传快照 → 取 vendor → 建 provider → generateInsight
→ parse → 失败静默/降级 → 写缓存 → ready
```

§6-49(d) 记录了「同纪律的第三个 AI 触点证明该模式已成熟，下次新 AI 触点直接照抄」——判断在当时是对的，但**现在应该反过来收敛**：

**修法**：抽一个共享的管道函数（**不是基类**，§6-50(b) 已经论证过「switch 就是最好的结构」，同理这里用函数 + 参数对象）：

```dart
// core/ai/ai_call_pipeline.dart（纯 Dart）
Future<AiCallResult> runAiCall({
  required AiGate gate,          // 关/同意/Key 三个短路条件 + 阈值（A6）
  required String? Function() readCache,
  required Future<void> Function(String) writeCache,
  required Object snapshot,       // 上传快照
  required String prompt,
  required int maxTokens,         // A4
  required String? Function(String) parse,
});
```

好处：安静原则的短路条件**只写一次**——未来加「数据量门槛」（A6）、加「单飞闸门」（D1）、加「自动重试」（D2），不会漏改某一路。保留各控制器自己的状态类型与 UI 语义（`AiInsightState` 八值降级 vs 静默 Idle 是**有意的差异**，不要抹平）。

> 这条可以等第四个触点出现时再做；但如果同时要做 A6/D1/D2，建议先收敛再改，否则要改三遍。

## 5. P2：增量能力（ADR-0006 边界内的新价值）

### C1 「AI 建议兑现追踪」——把解读从一次性读物变成可累积资产 ★ 最推荐

**现状缺口**：解读只保留当周一份，下周即被覆盖。产品自己宣称的闭环是「专注 → 数据 → 复盘 → 改进」，**但「上次的建议我做到了吗」这一环是断的**——AI 每周给一条建议，然后没有任何机制回头看它。

**实现成本极低**：
1. 缓存从 `{week, text}` 改成按周列表（保留最近 4~8 周）；
2. 统计页 AI 卡底部加一行**可折叠**的「上周 AI 建议」（`ExpansionTile` 或一行小字）；
3. **零新增 LLM 调用、零新增上传字段、零新增静默失败路径**，纯回看已有文本，完全符合安静原则。

**还能再进一步（本地判定，仍然不需要 LLM）**：部分建议是可量化的（如「把专注集中到上午」→ 比对本周时段分布上午占比是否上升），由 `InsightEngine` 输出一个三值判定（已见效 / 未见效 / 无法判定），展示成「上周建议：集中上午 · 本周上午占比 12% → 34%」。**这是把 AI 从「每周一篇读后感」变成「可验证的改进循环」的关键一步**，且判定逻辑全在本地纯 Dart 里，可单测。

> **2026-09-26 进展**：C1 所需的「跨周可回看的持久层」已由**记忆日志**
> （看板 #54 / [09-AI记忆日志规范](./09-AI记忆日志规范.md)）先落地——它按天记录
> `facts` + `note` + `insight`，天然跨周留存，且已排除在缓存覆盖之外。
> C1 剩余的部分因此缩到两件事：①统计页展示「上周建议」（从日志里取上周任一天的
> `insight`）；②`InsightEngine` 出三值判定。**新增 LLM 调用仍然为零。**

### C2 自定义 OpenAI 兼容端点 + 模型可覆盖

`LlmVendorConfig` 是三组 `const` 预设（`deepseek_provider.dart:39-57`），`model` 与 `endpoint` 都写死。加一个「自定义」项（endpoint + model + key 三个输入）约 20~30 行，**立刻解锁**：

- 智谱 GLM / 百川 / SiliconFlow 等国内服务商；
- **局域网内的 Ollama / LM Studio**——对隐私敏感用户是决定性优势（数据不出内网，且绕开「密钥要出设备」的顾虑）。

顺带：预设模型该更新了（DeepSeek 有 `deepseek-reasoner`、Kimi 有 k2 系列、通义 `qwen-turbo` 更便宜）。至少允许**在预设基础上覆盖 model 字符串**——同一套 UI，不加新厂商也能让用户自己选便宜模型。

### C3 API Key 输入：M500 上最大的落地摩擦

**问题**：M500 打字困难（§6-49(b) 已因此把问答做成 chip 点选），但**配置 API Key 需要手敲 `sk-` 开头的 30+ 位字符串**。这是当前 AI 功能最现实的失败点——想用的人卡在配置这一步。

**修法**：复用已有成熟通路。项目已有 `mikufocus_backup.json`（应用专属外存、免权限、文件管理器可见，看板 #45）——**支持导入 `mikufocus_ai_config.json`**（厂商 / endpoint / model / Key / 同意状态），用户在电脑上写好拷进设备同一目录 → 设置页 AI 区加「从配置文件导入」。

- 复用 `BackupCodec` 的校验风格（中文字面 FormatException、逐字段类型校验），纯 Dart 可测；
- 与已有备份机制同构，不引入新依赖、新权限；
- 附加价值：**换机/重置后一键恢复 AI 配置**。

> 如果 M500 有剪贴板通路，「从剪贴板粘贴」按钮是最轻的补充；但**文件导入更可靠**（可校验、可复用、可版本化）。

### C4 月度 / 4 周趋势解读（暂缓）

周维度之外的复盘是自然延伸，仍在 ADR-0006 边界内（仍是「解读已有数据」）。但建议**先做 C1**（兑现追踪）再看需求——C1 是对已有文本的复用，C4 是新请求、新成本、新 UI 面积，性价比低得多。

## 9. 一句话总结

现有 AI 模块的**骨架不用动**——本地算数 + 云端润色 + 三层短路 + 白名单出网这套设计是对的。真正要做的是**把喂给 LLM 的前提修对（A1/A2/A6）、把拿回来的答案接稳（A3）、别让它白等（A4）**，然后**用 C1 把每周一次的解读沉淀成可验证的改进循环**。前三类都是小改动，第四类是产品价值的真正增量。

## 10. 调性轮：论「枯燥」的根因与修法（2026-09-26，看板 #53）

> 触发：用户反馈「AI 功能太枯燥了」。
> 这一节补的是原任务书 §4（Prompt 契约）的**盲区**：它审了「数据够不够、
> 解析稳不稳、等得久不久」，唯独没审「读起来有没有意思」。

### 10.1 先诊断：枯燥不是「不够热情」

最容易走错的解法是「让 AI 说点好听的」——而那恰恰是 08-A5 花力气禁掉的东西。
把用户实际看到的输出摊开看，枯燥的来源有三层，**且第一层根本不在提示词里**：

| 层 | 症状 | 根因 |
| --- | --- | --- |
| **没料可说**（最根本） | 解读像把数字念了一遍 | 洞察里只有 8 个**孤立**数字，其中 3 个是总量。**能说的「关系」根本不存在于数据里**——中断落在哪个时段、最长一段出现在何时、哪一天最集中；这些原始数据（暂停时间戳、单段长度、会话日期）**一直在库里，只是从没被聚合过** |
| **表达被中性化** | 每周期读起来像同一个人写的 | 角色写的是「克制、务实」；硬约束只有「禁」（不写鼓励语 / 只描述数据 / 不用标题列表）；温度 0.3。三者叠加 → 对模型而言**最安全的写法就是照事实块逐行复述** |
| **结构单调** | 三段平铺 + 一条建议，没有层次 | 输出契约太平均，缺少「必须先给出一句有信息量的话」的强制 |

**关键的边界判断**：「表现不错」的毛病**不在于它是一句正面的话，而在于它把数字换成了形容词**——
读者看完不知道到底发生了什么。所以反鸡汤真正该禁的是**「没有信息量的表达」**，
不是「有性格的表达」。08-A5 那版把两者一起禁掉了，代价就是枯燥。

### 10.2 修法：先给料，再改口，最后保证「看得见变化」

1. **给料（B3）**：洞察扩 8 个字段，全部本地算、全部是时段/时长聚合。
   事实块从 8 行涨到 12~13 行——**行数本身就是「不枯燥」的前提**：
   有了一组可以互相比较的数字（时段之间、最长与平均之间、中断与专注之间），
   模型才有东西可以「发现」；只有总量时，它能做的只有复述。
2. **改口（E1）**：硬约束拆成三组，把「禁」和「要」分开写——
   【数字纪律】不变（第一红线）；【禁止空洞】精确化为「每句话都要对得回具体数字」；
   【要求具体】新增：至少给出一处数字之间的关系 / 反直觉处直接点出来 /
   **第一句必须是「发现」而不是「概述」** / 可以说人话、可以用比喻。
   角色同步由「克制、务实的助手」改为「擅长看出关系、说人话的复盘搭档」。
   温度 0.3 → 0.6：**数字确定性由硬约束 + 本地算数保证，不该拿温度去换**；
   温度只管措辞的多样性。
3. **增题（E2）**：数量不是重点，**题型**才是。「这天最值得说的是什么」是
   强制取舍的开放题——模型必须挑一个点讲，而不是把事实块平铺开。
4. **保证看得见变化（E3）**：缓存指纹并入 `kPromptVersion`。否则改了提示词，
   用户手里的旧缓存照样命中、读到的还是旧文风，看起来就像「改了没生效」。
   仍只给一行被动提示，**不自动重发**（安静原则不变）。

### 10.3 不变的东西（守住 ADR-0006）

调性放宽**只放宽语气，不放宽数据的可信边界**：

- 不上传任何新维度——8 个新字段全是时段/时长聚合，无应用名、无内容；
- 不做主动推送、不做聊天输入框、不让 AI 碰计时或统计决策；
- 失败仍静默、命中仍回看、过时仍只给一行被动提示；
- 单测继续钉住「零请求」与「不上传」两类断言（本轮新增 8 条）。

**一句话**：让 AI 不枯燥的正解是**给它更多可比较的数据、要求它把关系说出来**，
而不是让它说好听的。
