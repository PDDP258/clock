## 1. 评审对象与方法

- **基准**：以本团队已有方案（docs/01~03 + ADR + 已落地的 Flutter 脚手架）为主方案，HTML 报告仅作为评审对象与素材来源，不作为方案依据。
- **评审原则**：**UI 和功能简洁为主，体验最重要**。目标设备是 5 英寸小屏、以熄屏盲操作为核心场景的专用播放器——功能每多一个，无屏操作成本指数上升。
- **方法**：逐节比对 HTML 报告与主方案，结论分三类——技术错误（必须纠正）、产品问题（功能膨胀，必须收敛）、值得吸收（落实到具体文档）。

## 2. 技术错误清单（必须指出并纠正）

### 2.1 「按键直连 GPIO，所以不需要 audio_service」——错误且危险

- **HTML 怎么说的**：「整个方案**不需要** audio_service 插件，因为 M500 的按键不走蓝牙音频通道，而是直连主板的 GPIO 按键」，改用手写 `MediaSession.Callback` + flutter_foreground_task。
- **为什么错**：直连只解决**事件来源**（按键事件本地可靠产生），不解决**事件路由**。熄屏/后台时，系统只把媒体键分发给持有 active MediaSession 的 App——没有活跃会话，按键事件根本不会到达本 App。而 audio_service 恰好免费提供了这一整条管道：MediaSession 管理 + `mediaPlayback` 类型前台服务 + 锁屏/通知（MediaStyle）集成。手写裸 MediaSession + flutter_foreground_task 是重复造轮子，且在音频焦点、会话释放、后台回收等边角上更容易出 bug。
- **我们的正确做法**：维持 audio_service + 静音保活霸占 MediaSession（计时开启霸占、结束/暂停超时释放归还音乐 App）。
- **对应 ADR**：ADR-0001；驳斥正文已补入 [技术架构设计 §5.1](./03-技术架构设计.md)。

### 2.2 flutter_foreground_task `repeat(1000)` 每秒唤醒做计时——反模式

- **HTML 怎么说的**：用 `ForegroundTaskEventAction.repeat(1000)` 让前台服务每秒回调一次，以此驱动计时。
- **为什么错**：每秒唤醒费电；在 Doze 与后台限制下不可靠；且把「计量」与「渲染刷新」错误耦合——刷新一断，计时就漂。
- **我们的正确做法**：时间戳差值计时（只记录锚点时间戳，剩余时间 = 时长 − 差值），`Clock` 抽象注入假时钟，纯 Dart 可单测；熄屏、杀进程、系统休眠均不影响计量精度（`lib/core/timer/timer_engine.dart` 已实现并有测试）。
- **对应 ADR**：架构决策见 [技术架构设计 §4.1](./03-技术架构设计.md)（已补明确拒绝语句）。

### 2.3 代码示例张冠李戴、FN 键码靠猜——生成质量不可靠

- **HTML 怎么说的**：标注为「Flutter 端 - 媒体按键处理」的 `MediaButtonHandler` 示例里写的是 Kotlin 代码（`override fun onMediaButtonEvent(intent: Intent)`，且直接调用 `timerBloc.togglePlayPause()`）；FN 键 KeyCode 直接猜测为 `KEYCODE_FUNCTION`，未实测。
- **结论**：该报告代码级内容不可直接采信，仅可作研究素材参考。FN 键码不靠猜——以我们的按键自检工具实测为准（见 [技术架构设计 §5.6](./03-技术架构设计.md) 与 PRD US-G02）。

### 2.4 Drift + Hive 双库——无谓的复杂度

- **HTML 怎么说的**：Drift 处理复杂查询（统计），Hive 存配置与缓存。
- **为什么错**：两套存储体系 = 两套 schema、两套迁移、两份依赖。对一个时钟 App 的配置与键值存储需求，shared_preferences 完全足够，双库是过度设计。
- **我们的正确做法**：drift（结构化数据）+ shared_preferences（配置与按键映射表）。
- **对应 ADR**：ADR-0002；[技术架构设计 §6](./03-技术架构设计.md) 已确认选型并明确排除 Hive。

## 3. 产品批判清单（功能膨胀，违背「简洁为主、体验第一」）

### 3.1 6 种计时模式 MVP 全上——选择瘫痪

HTML 把番茄 / 50-10 / 正计时 / Flowtime / 自定义间隔 / 倒计时冲刺 6 种模式全部塞入规划。在免触屏设备上，「切换模式」本身就是最贵的操作之一，模式越多盲操作越不可记忆。**收敛为 2 种**：番茄倒计时（默认 25/5）+ 正计时；50/10 仅作为番茄钟的时长预设（V0.2，附深度工作推荐说明）。

### 3.2 按键映射过载且自相矛盾

HTML 给每枚键都排满短按/长按/双击（如「上一首长按 = 查看今日统计摘要」）——**不看屏幕怎么看统计摘要？** 免触屏场景下这是自相矛盾的设计。砍至极简映射：单按 = 开始/暂停、长按 = 结束并保存、下一曲 = 跳过阶段、上一曲 = +5 分钟（正计时 = 打点）；双击/三击保留解析能力但默认不映射（ADR-0005）。

### 3.3 成就等级 / AI 建议 / 社交自习室 / 穿戴联动——砍掉或打入 backlog

对一台 5 英寸小屏自律时钟，这些是教科书级的功能堆叠：成就/等级/商店制造游戏化疲劳（正是调研痛点 Top3）；「AI 专注建议」无数据基础、属噱头；社交自习室与「远离手机、独处专注」的定位相悖；穿戴联动需要抬腕触屏，与零触屏理念冲突。激励体系只保留轻量的「弹性连续」（V0.4）。

### 3.4 心率 / 天气 / 位置采集——隐私越界

HTML 的「数据采集扩展点」列出心率、步数、天气、位置等维度。一个时钟 App 采集心率与位置没有正当性，**明确不做**（隐私红线，见 PRD「已砍掉不做」清单）。

### 3.5 定位话术与场景不符

HTML 的一句话定位是「戴上耳机，按下播放键，开始专注」——这是蓝牙耳机场景的话术，与我们「M500 播放器机身实体键」的场景不符，已按播放器场景重写（PRD Solution）。

## 6. 结论

一句话：**HTML 方案「研究素材有价值、技术方案有硬伤、功能规划无克制」**——吸收其研究素材与 4 个设计依据（中断成本 23 分钟、Fogg B=MAP、弹性连续、按键自检），拒绝其技术路线（弃用 audio_service 的裸 MediaSession、每秒轮询计时、Drift+Hive 双库）与功能堆叠（6 模式 / 成就 / AI / 社交 / 穿戴 / 无关数据采集）。全部结论已落实为 ADR-0005 与 PRD、架构、词汇表、代码的对应修改。

## 7. 附带发现：主方案自身的一处内部矛盾

评审过程中发现**我们自己的文档**也存在一处矛盾：PRD 按键映射表称「空闲时单按播放键 = 开始新番茄」，但 ADR-0001 的仲裁策略是「仅计时开启时霸占 MediaSession」——空闲时按键归音乐 App，按键事件根本到不了本 App，「空闲时按键开始」无法成立。缓解路径：首次开始走触屏大按钮 / 通知按钮，V0.2 由 FN 键承担「一键开始上次模式」（FN 走独立的原生按键通道，不依赖媒体会话）。已在 ADR-0005 Consequences 中注明。
