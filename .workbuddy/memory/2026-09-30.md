### 关键判定：设备是 1280×720 横屏
参考截图量出来是 1280×720 → 屏幕长边/短边 S = 16/9 = 1.7778。
两条规则本质是同一个 `cover + 顶对齐`，区别只在**哪一边溢出**：

- 规则 1（`r >= S`，比 16:9 更宽）：按高缩放，高 = 720，宽溢出 → 纵向无溢出 → **背景固定**
- 规则 2（`r < S`）：按宽缩放，宽 = 1280，高溢出 → 顶置 → **背景随内容 1:1 滚动**（夹到 maxScroll）

判定用整数交叉相乘 `w*720 >= h*1280`，避免 2048×1152 正好等于 16:9 的浮点抖动。

### 踩到的坑
1. **Kotlin `MethodCall` 是顶层类，不是 `MethodChannel` 的嵌套类**。`import io.flutter.plugin.common.MethodChannel.MethodCall` + 签名 `MethodChannel.MethodCall` 双双 unresolved，编译挂了三次才定位（`flutter analyze` 查不到 Kotlin 错误，只能靠 `flutter build apk`，每次 1~3 分钟）。**以后改 Kotlin 必须出包验证**。
2. **EXIF 旋转**：`BitmapFactory` 不看 EXIF，相机竖图不处理就是躺着的背景。解法是探测阶段就把宽高**交换后上报**，让 Dart 的判定与最终成图一致（不能在原生侧偷偷转完还上报旧尺寸）。
3. **透明图压平色两条通道必须同色**：Python 脚本原压白底、Kotlin 压黑底 → 统一改黑（App 常驻深色主题）。当前 26 张源图无一带 alpha，未触发重跑。
4. **Windows 单测 tearDown 删临时目录偶发「文件被占用」** → 包 try/on FileSystemException。
5. `StateNotifier` 的 `state=` 在 dispose 后会抛 → `reroll()` / 定时器回调都要 `mounted` 守卫。

## 同晚真机反馈调参（第二包）

## 第三轮：详细页按溢出深度加权（第三包）

用户反馈「详细时间统计页尽量使用满足 2 的图片（概率提高）」。排查发现：
详细页本来就**只从规则 2 池**抽（非概率问题），但池里 22 张有 **7 张是浅横构图**
（铺满屏后纵向溢出仅 28~185px，如 bg_conv14 1280×748），它们滚到底也只挪一指宽，
观感与规则 1 无异——均匀抽取时这 7 张占走 32% 出现概率，这才是「感觉规则 2 不够多」的根源。

修正：`BgPagePolicy` 增 `weightOf`，详细页策略挂 `bgScrollDepthWeight`
（权重 = 铺满 1280×720 后的纵向溢出像素，规则 1 恒 0）；`bgPickImage` 加轮盘赌加权抽取，
**权重全 0 回退均匀**（防加权反而抽不出图，如回退全池后只剩规则 1 图的场景）。
加权后 7 张浅图合计概率 32%→约 4%（不是硬剔除），深竖图（溢出 1~3 屏）主导。

- 测试 +5：权重值断言 / 20000 次统计分布（深>中>浅、浅<8% 且 >0）/ 零权重回退 /
